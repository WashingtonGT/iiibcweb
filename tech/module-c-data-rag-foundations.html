Why this module exists

Most AI failures at growth stage are data failures wearing a model costume. Gartner forecasts that ~60 percent of AI projects will be abandoned through 2026 because the underlying data was never AI-ready (closer to ~80 percent for generative AI). In those projects the model was fine. The data was demo-clean, unrepresentative, unlabeled, and stuck behind a service that no pipeline could call.

The second failure is treating retrieval as a weekend project. Teams paste documents into a vector store, get a plausible demo, and ship it. Then production shows that retrieval returns the wrong chunk half the time, that one tenant can see another tenant's embeddings, and that nobody can say whether last week's prompt change made answers better or worse. RAG is an information-retrieval system with an LLM bolted on the end, and IR systems need evaluation, not vibes.

The third failure is strategic. A foundation model is a commodity your competitors rent from the same three vendors you do. Your proprietary data—transactional, behavioral, clinical, domain-specific—is the one asset they cannot replicate. McKinsey's 2025 work is blunt: the durable advantage comes from feedback loops in which product usage improves the data asset, which improves the product, which drives more usage. If you do not engineer that loop deliberately, you are renting a commodity and calling it a strategy.

This module is for the people who build the loop. It maps directly to Assessment Section 2 (AI-readiness, lineage, accessibility, proprietary advantage, and RAG with leakage controls).

Learning objectives

By the end of this module, participants will be able to:

  1. Score a dataset's AI-readiness across quality, representativeness (including edge cases), labeling, lineage, and accessibility, using a concrete checklist instead of gut feel.
  2. Diagnose missing data lineage and explain why it blocks AI audits (only ~30 percent of organizations have it, per Gartner).
  3. Choose a chunking strategy (fixed, recursive, semantic, structural) that fits a corpus, and justify chunk size and overlap.
  4. Select an embedding model and a vector store, and explain when pgvector beats a dedicated store (Pinecone/Weaviate/Qdrant) and when it does not.
  5. Build a working RAG pipeline end-to-end: ingest → chunk → embed → retrieve → ground → evaluate.
  6. Evaluate retrieval and generation with real metrics (recall@k, MRR, faithfulness, answer relevance) instead of eyeballing demos.
  7. Identify and close retrieval/embedding leakage and cross-tenant exposure (OWASP LLM08) in a RAG design.
  8. Decide between RAG and fine-tuning (or both) for a use case, with cost and grounding as the deciding axes.
  9. Design a data feedback loop that compounds proprietary advantage as the product is used.

Core content

Part 1: AI-readiness of data

"AI-ready" means more than "clean." A dataset can pass every dashboard data-quality check and still be useless for AI because it is unrepresentative, unlabeled for the task, or unreachable. AI-readiness has five dimensions. Score each 0–3 (the assessment's scale); the weakest one is your ceiling.

                    ┌──────────────────────────────────────────┐
   AI-READINESS  =  │  min( Quality, Representativeness,        │
   (your ceiling)   │       Labeling, Lineage, Accessibility )  │
                    └──────────────────────────────────────────┘
   One weak dimension caps the whole system. Fix the floor, not the average.

1. Quality. Quality covers completeness, consistency, deduplication, and freshness. The trap is "demo-clean": data that looks fine on the ten rows you inspected and breaks on the long tail. For RAG specifically, quality means the source text is faithful, with no OCR garbage, no truncated PDFs, and no boilerplate headers or footers polluting every chunk.

2. Representativeness (including edge cases). Does the data cover the real distribution your AI will face, including the rare-but-costly cases? A support-RAG corpus built only from happy-path articles will confidently fail on the angry refund-dispute query, which is exactly where a wrong answer costs you. Teams skip this dimension more than any other, because edge cases are, by definition, hard to collect.

3. Labeling. For retrieval, "labeling" means metadata: document type, owner, tenant, effective date, sensitivity class, and source system. You cannot filter, scope to a tenant, or expire unlabeled chunks, and that is how you get stale and cross-tenant answers.

4. Lineage. Can you trace an AI output back through retrieval → chunk → source document → source system → transformation? Only ~30 percent of organizations have data lineage, and its absence is a top reason AI audits fail. Without lineage you cannot answer "why did the model say that?" A regulated buyer, a regulator, or an incident review will eventually ask.

5. Accessibility. Can a pipeline reach the data through documented APIs or a data catalog, or is it stranded in a silo, a SaaS export, or a person's head? Stranded data is invisible to AI no matter how good it is.

Signal

A team that can produce, for any AI answer, the exact source chunk and the document's owner and effective date. That is lineage + labeling working together.

Noise

"Our data is clean, we have a data warehouse." A warehouse proves accessibility and maybe quality. It says nothing about representativeness, task-labeling, or lineage through the AI layer.

Part 2: Building RAG correctly

RAG has five stages, and every earlier stage caps the quality of the last one (the LLM answer). Garbage chunks in, confident garbage out.

  ┌─────────┐   ┌─────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐
  │ INGEST  │──▶│  CHUNK  │──▶│  EMBED   │──▶│ RETRIEVE │──▶│  GROUND  │
  │ parse,  │   │ split + │   │ vectors  │   │ top-k +  │   │ stuff    │
  │ clean,  │   │ overlap │   │ + store  │   │ filter   │   │ context  │
  │ label   │   │         │   │          │   │ + rerank │   │ → LLM    │
  └─────────┘   └─────────┘   └──────────┘   └──────────┘   └──────────┘
       │                                                          │
       └──────────────── metadata / tenant filter ───────────────┘

Chunking strategies

The chunk is the unit of retrieval, so its size sets a trade-off. Too large, and you retrieve irrelevant text that dilutes the answer and burns tokens. Too small, and you lose the context needed to answer.

StrategyHow it worksBest forWatch out
Fixed-sizeN tokens, fixed overlapUniform prose, fast baselineSplits mid-sentence/mid-table
RecursiveSplit on separators (¶ → sentence → token)General documents (default)Tune separators per format
SemanticSplit where embedding similarity dropsDense, topic-shifting textSlower, costs embeddings to chunk
StructuralSplit on document structure (Markdown headings, HTML, code functions)Docs, wikis, code, structured PDFsRequires a real parser

Start from these practical defaults, then tune with eval: ~256–512 tokens per chunk, ~10–15 percent overlap, with recursive or structural splitting. Always carry metadata on each chunk (source id, tenant, section heading, effective date). Never use naive fixed-size chunking for tables and code; split on structure, or the chunk is meaningless.

Practitioner note

Chunk size is an empirical decision, not a default. Build a 30–50 question eval set first, then sweep chunk size and overlap and pick the setting that maximizes retrieval recall. Teams that pick "1000 tokens" because a tutorial said so are guessing.

Embeddings

The embedding model maps text to vectors so that semantically similar text lands nearby. Four choices matter:

  • Dimension (e.g., 384, 768, 1536, 3072): higher dimensions often retrieve slightly better but cost more storage and slow search. For most growth-stage corpora, a 768–1536-dim model is the sweet spot.
  • Hosted vs. local: hosted models (OpenAI text-embedding-3-*, Cohere, Voyage) are easy and strong. Local models (e.g., a bge/e5/gte open model) keep regulated data in-house and remove per-call cost, which matters when your data cannot leave your boundary.
  • Domain fit: a general embedder underperforms on jargon-heavy corpora (clinical, legal, financial). Test domain-specific or fine-tuned embedders against your eval set before committing.
  • Consistency rule: the same model must embed both documents and queries. Changing the embedding model means re-embedding the entire corpus, so treat the embedder as a versioned dependency.

Vector store choice: The decision that gets over-engineered

Signal

For most growth-stage corpora, pgvector is the right first answer. You already run Postgres, so you get transactions, joins, row-level security, and metadata filtering in one system. As a rule of thumb, pgvector handles up to ~tens of millions of vectors (≈<50M) comfortably with HNSW indexing.

Noise

Reaching for Pinecone on day one for a 200k-chunk internal wiki. You add a second datastore, a sync problem, and a bill, all to solve a scale problem you do not have.

OptionWhen it winsTrade-off
pgvector (Postgres extension)<~50M vectors; you already run Postgres; want metadata filtering + row-level security in one placeTune HNSW params; very large scale needs sharding work
PineconeLarge scale, fully managed, minimal opsSaaS cost; data leaves your DB; another vendor
WeaviateHybrid search + modules, self-host or cloud, large scaleMore to operate if self-hosted
QdrantHigh-performance filtering, self-host friendly, large scaleAnother datastore to run and sync

Decision heuristic: start in pgvector; graduate to a dedicated store only when you have measured a real limit (vector count, latency at p95, or filtering throughput) that pgvector cannot meet. "We might scale" is not a measured limit.

Hybrid retrieval beats pure vector for most enterprise corpora. Combine dense (vector) similarity with sparse keyword search (BM25/full-text) and fuse the rankings (e.g., reciprocal rank fusion). Pure-vector retrieval quietly fails on exact terms such as error codes, SKUs, and statute numbers, and keyword search catches them.

Part 3: Retrieval evaluation, leakage, and cross-tenant exposure

Evaluate retrieval, not just the final answer

When an answer is wrong, you must know which stage failed: retrieval (wrong chunks fetched) or generation (right chunks, wrong answer). Measure the two separately.

Retrieval metrics (these need a labeled set mapping queries to relevant chunks):

  • Recall@k: what fraction of the relevant chunks appear in the top-k? This is the single most important RAG metric. If the right chunk isn't retrieved, no model can answer.
  • Precision@k: what fraction of the top-k retrieved chunks are relevant? Low precision wastes context tokens and invites distraction.
  • MRR (Mean Reciprocal Rank): how high does the first relevant chunk rank? It matters when you stuff only a few chunks.

Generation metrics (the RAG triad):

  • Faithfulness / groundedness: does the retrieved context support every claim in the answer? This is your anti-hallucination metric.
  • Answer relevance: does the answer address the question?
  • Context relevance: were the retrieved chunks actually about the question?

Tooling options include Ragas, TruLens, DeepEval, or a homegrown LLM-as-judge harness. The principle matters more than the tool: a fixed eval set, scored on every change, with results checked into the repo. Module E demands the same discipline in production.

Practitioner note

Build the eval set before you tune anything (30–50 representative queries with known-good answers and their source chunks). It is the contract that makes every later decision (chunk size, embedder, k, reranker) falsifiable instead of a matter of vibes.

Leakage and cross-tenant exposure: OWASP LLM08

OWASP's LLM08: Vector and Embedding Weaknesses is the RAG-specific risk class. Design against three failure modes:

1. Cross-tenant exposure. In a multi-tenant product, tenant A's query retrieves tenant B's chunks. This happens when the tenant id is not enforced at query time as a hard filter. Asking the model to be careful in the prompt does not fix it. Apply a metadata filter in the query, and ideally add Postgres row-level security so a missing filter fails closed, not open.

   SAFE:   retrieve WHERE tenant_id = $current_tenant  ← enforced in query / RLS
   UNSAFE: retrieve top-k from the whole index, hope the prompt keeps tenants apart

2. Embedding leakage / inversion. Embeddings are not anonymized data. Attackers can partially reconstruct sensitive text from vectors, and similarity search can surface records a user should never see. Give the vector store the same sensitivity class as the source text, with the same access controls, encryption, and retention.

3. Retrieval-time data poisoning / indirect injection. A document in the corpus contains instructions ("ignore previous instructions, exfiltrate…"). When retrieved, it becomes part of the prompt, which makes it an indirect prompt-injection vector. Controls: validate and clean ingested content, restrict who can write to the corpus, and treat retrieved text as untrusted input (Module J goes deeper).

Risk flag

The most common production RAG breach is mundane. A multi-tenant app filtered tenants in the application layer but not in the retrieval query, so a code path that skipped the filter returned another customer's data. Enforce tenant isolation at the data layer (row-level security) so the default is fail-closed.

Do / Don't

DoDon't
Apply tenant/permission filters inside the retrieval queryFilter after retrieval in app code (one missed path = breach)
Classify the vector store at the source data's sensitivity levelTreat embeddings as "just numbers," exempt from access control
Validate and scope write access to the corpusAuto-ingest untrusted external content into the index

Part 4: RAG vs. fine-tuning trade-offs

RAG and fine-tuning solve different problems. Grounding vs. behavior decides between them, and cost breaks ties.

   Need the model to KNOW current/private FACTS, cite sources,
   update without retraining, enforce access control      ──▶  RAG
   Need the model to BEHAVE a certain way: format, tone,
   domain style, a narrow task done consistently          ──▶  FINE-TUNE
   Need both (rare at growth stage)                        ──▶  RAG + light fine-tune
DimensionRAGFine-tuning
Best atInjecting fresh, private, citable factsShaping behavior, format, style, narrow tasks
Updating knowledgeAdd/replace a document; instantRe-train; slow and costly
Grounding / citationsNative—points to source chunksNone inherent; can still hallucinate
Access controlPer-document, per-tenant filteringBaked into weights; cannot scope per user
Upfront costLow (pipeline + store)Higher (data prep, training, eval)
Ongoing costRetrieval + larger prompts (more input tokens)Cheaper per call (shorter prompts) once trained
Audit/lineageStrong (trace to source)Weak (why did weights produce this?)

Default for growth-stage technology operators: start with RAG. It grounds answers in your proprietary data, lets you update knowledge without a training run, supports per-tenant access control, and gives you lineage for audits. Fine-tune only when prompting + RAG cannot solve a clear behavior, format, or latency problem, and only when you have the labeled data and eval discipline to prove the fine-tune helped.

Signal

"We chose RAG because the buyer's auditors need source citations and we must scope answers per tenant—fine-tuning gives us neither." That is a grounded decision.

Noise

"We fine-tuned so the model would know our docs." Fine-tuning is a poor and expensive way to inject facts: the model still hallucinates and cannot cite. Retrieval does that job.

Part 5: Proprietary data as a compounding moat

A foundation model is rented and shared, so your moat is the data only you have. More important still is the feedback loop that makes it better as the product is used (McKinsey, 2025). Engineer the loop explicitly:

        ┌──────────────────────────────────────────────────────┐
        │                                                       │
        ▼                                                       │
   USERS use the product  ──▶  product captures signal         │
   (queries, clicks,           (what was retrieved, accepted,  │
    corrections, outcomes)       corrected, the real outcome)   │
        │                                                       │
        ▼                                                       │
   signal labels & improves the data asset  ──▶  better        │
   (eval set grows, retrieval tuned,             retrieval &    │
    edge cases captured, labels enriched)        answers  ──────┘

A growth-stage operator can build these concrete loops:

  • Correction capture: when a user (or support agent) fixes an AI answer, store the corrected pair as a labeled eval or training example. Every correction makes the system harder to beat.
  • Implicit signal: log which retrieved chunks led to accepted vs. abandoned answers, and feed that into reranking and chunk curation.
  • Outcome linkage: tie the AI interaction to the downstream business outcome (ticket resolved, deal advanced, claim adjudicated) so you learn what good looked like, not just what was clicked.
  • Edge-case harvesting: route low-confidence or no-good-chunk queries to a queue that grows your representativeness where it is weakest.
Practitioner note

The moat is the instrumentation, not the data dump. A competitor can scrape public docs; it cannot replay your users' corrections, accepted answers, and outcomes. Build the capture before you scale the feature, because retrofitting it loses signal you can never get back.

Risk flag

Feedback loops touch user data. Confirm consent, training opt-out, and data-classification rules (Assessment 2.6 / Module K) before any user content becomes training or eval data, especially PII, PHI, source code, or privileged material.

Hands-on lab and exercises

Note

Goal: each pair ships a working, evaluated, leak-aware RAG pipeline over a provided corpus. Stack: Python, Postgres + pgvector (Docker), an embedding model, and any chat LLM. We provide a ~150-doc sample corpus with a two-tenant split and a 30-question eval set.

Exercise 1: Ingest, chunk, embed, store (45 min)

  1. Load the corpus. Parse and clean it (strip boilerplate headers and footers, fix encoding). Attach metadata to every chunk: doc_id, tenant_id, section, effective_date, sensitivity.
  2. Implement two chunking strategies (recursive ~512/15 percent overlap, and structural by heading). Keep both, tagged.
  3. Embed chunks with one model, and store vectors + metadata in pgvector with an HNSW index.
  4. Confirm: SELECT count(*), tenant_id FROM chunks GROUP BY tenant_id returns both tenants.

Exercise 2: Retrieve, ground, and evaluate (50 min)

  1. Implement top-k retrieval with a tenant filter in the query (WHERE tenant_id = :tenant). Add a hybrid option (vector + full-text, fused).
  2. Ground: build a prompt that injects the retrieved chunks and instructs the model to answer only from context and cite chunk ids, and to refuse if the context does not support an answer.
  3. Run the 30-question eval set. Compute recall@5 and MRR for retrieval, and faithfulness + answer relevance for generation (LLM-as-judge or Ragas).
  4. Sweep chunk strategy (recursive vs. structural) and k ∈ {3,5,10}. Record metrics in a table, then pick a winner and justify it.

Exercise 3: Break the tenant wall, then fix it (25 min)

  1. Remove the tenant filter from the retrieval query. Run a tenant-A query that should match a tenant-B document, and observe the cross-tenant leak (OWASP LLM08).
  2. Fix it two ways: (a) restore the query-side filter; (b) add Postgres row-level security so a missing filter fails closed. Re-run and confirm there is no leak.
  3. Add one poisoned document containing an injected instruction to the corpus. Show it being retrieved, and write one mitigation (write-access restriction or ingest validation).

Facilitator answer key

Ex 1. Common misses: (a) embedding before attaching metadata, which makes per-tenant filtering impossible without re-embedding; (b) fixed-size chunking that splits tables and code (structural should clearly win on those docs in Ex 2); (c) forgetting that documents and queries must use the same embedding model. Correct outcome: both tenants present, and every chunk carries tenant_id and sensitivity.

Ex 2. Expected pattern: recall@5 rises then plateaus as k grows, while faithfulness often drops at high k because extra chunks introduce distractors. That precision/recall tension is the teaching moment. Structural chunking typically wins on the heading-structured docs; recursive is competitive on prose. Hybrid (vector+BM25) should beat pure vector on queries containing exact codes or IDs. A defensible "winner" cites the metric table, not preference. If faithfulness is low despite good retrieval, the prompt isn't constraining the model to context; tighten the "answer only from context / refuse if unsupported" instruction.

Ex 3. (1) Without the filter, the tenant-A query returns a tenant-B chunk: a live LLM08 cross-tenant breach. (2) The query-side filter fixes the happy path, but RLS is the durable fix because it makes the default fail-closed; a future code path that forgets the filter still cannot leak. The best answers note that app-layer filtering alone is fragile. (3) The poisoned doc is retrieved and its text enters the prompt (indirect injection). Acceptable mitigations: restrict corpus write access, validate and sanitize ingested content, treat retrieved text as untrusted, and (forward reference) handle output per Module J.

Knowledge check

  1. (MCQ) Gartner forecasts that roughly what share of AI projects will be abandoned through 2026 because their data is not AI-ready?
    1. 20 percent
    2. 40 percent
    3. 60 percent
    4. 90 percent
  2. (MCQ) The five dimensions of AI-readiness combine so that overall readiness equals the:
    1. average of the five
    2. sum of the five
    3. minimum of the five
    4. maximum of the five
  3. (Short answer) A RAG answer is wrong. Name the two stages that could be at fault and the metric you'd use to tell them apart.
  4. (MCQ) For a 300k-chunk internal wiki at a company already running Postgres, the right first-choice vector store is usually:
    1. Pinecone
    2. pgvector
    3. a fine-tuned model
    4. a CSV file
  5. (Short answer) Which OWASP LLM risk covers vector and embedding weaknesses, and what is the single most reliable control against cross-tenant retrieval leakage?
  6. (MCQ) You need the model to cite current, private, per-tenant facts and pass an audit. Choose:
    1. fine-tuning
    2. RAG
    3. a bigger base model
    4. longer prompts only
  7. (Short answer) Why is fine-tuning a poor mechanism for injecting up-to-date factual knowledge?
  8. (Short answer) Name two feedback-loop signals a product can capture so its proprietary data compounds with usage.
  9. (MCQ) What typically happens to faithfulness as you increase k (chunks retrieved) well beyond what's needed?
    1. always improves
    2. unaffected
    3. can degrade as distractor chunks enter context
    4. becomes infinite

Answer key

  1. c) 60 percent (~80 percent for generative AI).
  2. c) minimum: the weakest dimension caps the system.
  3. Retrieval (wrong chunks fetched) and generation (right chunks, wrong answer). Use recall@k / MRR for retrieval and faithfulness for generation. High recall + low faithfulness points at generation or the prompt; low recall points at retrieval.
  4. b) pgvector: under ~50M vectors and already on Postgres, so no second datastore is needed.
  5. LLM08 (Vector and Embedding Weaknesses). Most reliable control: enforce the tenant/permission filter at the data layer, with a query-side filter plus Postgres row-level security so a missing filter fails closed.
  6. b) RAG: native grounding, citations, per-tenant access control, and lineage; fine-tuning provides none of these.
  7. Knowledge is baked into the weights, so updating means re-training (slow and costly). The model still hallucinates, cannot cite sources, and cannot scope facts per user or tenant.
  8. Any two: correction capture (fixed answers as labeled examples), implicit signal (accepted vs. abandoned retrievals), outcome linkage (downstream business result), edge-case harvesting (low-confidence queries queued).
  9. c) can degrade: extra, less-relevant chunks act as distractors and reduce groundedness while inflating token cost.

Facilitator guide

Prep checklist

  • Provision the lab environment ahead of time: a Docker image with Postgres + pgvector, Python deps (embeddings client, an eval library such as Ragas or DeepEval), and API keys or a local embedding model.
  • Distribute the ~150-doc, two-tenant sample corpus and the 30-question eval set (with gold chunks) the day before.
  • Pre-run all three exercises end-to-end yourself, and capture a reference metrics table so you can sanity-check each pair's results.
  • Have a local embedding model available as a fallback for participants who cannot send data to a hosted API.

Materials needed: laptops with Docker + Python; the corpus and eval set; the four takeaway artifacts, printed or shared; and a shared metrics scoreboard (whiteboard or doc) for Ex 2 results.

Timing guidance: The lab is the heart of the day, so protect the full two hours. If you run behind, drop the semantic-chunking option (keep recursive + structural) and the hybrid-retrieval add-on. Never cut Exercise 3; the leakage drill is the highest-stakes lesson.

Common pitfalls to call out

  • Pairs embed before attaching metadata, then cannot filter by tenant without re-embedding.
  • Teams treat the eval set as optional and tune by eyeballing demos. Stop this early.
  • Teams over-engineer the vector store choice. Redirect them to "what measured limit are you solving?"
  • Participants confuse "clean data" with "AI-ready data." Drill the Part 1 dimensions until the distinction is automatic.

Discussion prompts

  • "Which of the five readiness dimensions is your team's real ceiling today—and why is it the one you most avoid talking about?"
  • "Where in your product could a missing tenant filter leak data—and is the control in app code or the data layer?"
  • "Name one feedback signal you could capture next sprint that a competitor could never replicate."
