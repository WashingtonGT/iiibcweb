Why This Module Exists

Most teams measured AI wrong from day one. They watched coding get faster, declared victory, and missed that coding was never the whole job. Research and field experience put coding at only 30–40% of engineering effort — the other 60–70% is system design, requirements clarification, code review, testing, incident response, and managing technical debt. A 10x speedup on the small slice produces only a 2–3x overall gain when the surrounding process is untouched. One platform team at a 2025 engineering summit found incident response alone ate 32% of capacity in a single week. No coding assistant fixes that. Visibility does.

The cost of skipping this module is concrete: fast wrong code at scale, reviewers drowning in 500-line generated diffs they rubber-stamp, runaway token spend that rivals the cloud bill, and "agent tech debt" — code no human ever fully understood. These are new risk classes that did not exist three years ago. Velocity without spec discipline and verification capacity is a liability, not an advantage.

The opposite is also proven. A full OAuth2 ticket — planned, implemented, and reviewed by a chain of specialized agents — went from open to PR in 8 minutes at roughly $1.00, against two human-days for the same work. The economics work because the process was redesigned, not because the tools were exotic. The tools are commodity. The discipline is the moat.

This module trains that discipline for growth-stage operators: spec-first development, controlled agent chains, agent-ready codebases, and conscious management of the L1–L5 cost curve.

Learning Objectives

By the end of this module, participants will be able to:

  1. Locate the real constraint — measure where engineering time actually goes before claiming an AI productivity win, and explain why a 10x coding speedup yields only ~2–3x overall.
  2. Write a peer-reviewable spec — produce a requirements.md / design.md / tasks.md set for a real ticket, checked into the repo and versioned, so the spec is what gets reviewed.
  3. Control an agent instead of vibe-coding — scope a task, manage context, and critically review an AI-generated diff against the spec rather than accepting it.
  4. Run a multi-agent chain — orchestrate a planner → implementer → independent reviewer flow and explain why no single agent is trusted end-to-end.
  5. Make a repo agent-ready — author an AGENTS.md, define clean module boundaries, and scope agent permissions.
  6. Place the team on the L1–L5 maturity/cost curve and apply model specialization (expensive reasoning for planning, cheap fast models for bulk implementation) to control token spend.
  7. Apply a spec-review checklist as a gating artifact and reject specs that fail it.
  8. Reproduce the OAuth2 proof point in the sandbox: open-to-PR via a chained agent run, and read the cost/time it produced.

Core Content

Part 1 — Coding Was Never the Bottleneck

The output of any system is set by its constraint, not its strongest component. For two decades the constraint in software was writing code. LLMs are dismantling that. As coding accelerates, the constraint moves to what happens before and after the code — and most organizations have not yet found where it landed.

   Where engineering time actually goes (directional)
   ┌──────────────────────────────────────────────────────┐
   │ Coding              ████████████  30–40%              │
   │ Surrounding work    ████████████████████████  60–70%  │
   │   incident response · system design · code review     │
   │   requirements · testing · meetings · tech debt       │
   └──────────────────────────────────────────────────────┘

   10x faster coding, process unchanged  →  ~2–3x overall gain
   (Amdahl's law applied to engineering: you can only speed up
    the part you actually accelerated.)
Signal

Before you celebrate an AI productivity number, instrument where time goes. A team that learns incident response is 32% of capacity has found a constraint no coding assistant can touch.

Noise

"We adopted Copilot and merged 40% more PRs." More PRs of what quality? Velocity reported without a paired quality metric is motion mistaken for progress.

The new measurement stack (covered in depth in Module M; introduced here because you cannot redesign what you cannot see):

Old metricNew metric
Lines of codeAI code share (% AI-generated)
PR / raw velocityComplexity-adjusted velocity
Defect countCode turnover ratio (how much code is rewritten soon after merge)
Cost per engineerCost per ticket / cost per feature
Annual engagement surveyQuarterly DX pulse

Without these, AI investment is unfalsifiable — you can neither prove nor disprove it worked.

Practitioner note

The framework that organizes this whole module: shift from "AI assists the engineer" to "AI executes; the engineer specifies and verifies." Everything downstream — specs, chains, agent-ready repos — follows from that one sentence.

Part 2 — Spec-First Development: The Spec Is the New Code Review

When AI writes the code, your leverage moves upstream. The highest-value artifact you produce is no longer the diff — it is the specification the diff must satisfy. Reviewing 50 lines of spec is worth more than reviewing 500 lines of generated code, because the spec is where intent, constraints, and acceptance criteria live, and because a wrong spec generates wrong code at machine speed.

Spec-first (a.k.a. spec-driven) development means: specs and tests are checked into the repo, versioned, and peer-reviewed — exactly like code. The industry-standard shape (popularized by GitHub's Spec Kit and the broader spec-driven movement) is a three-file pattern that lives beside the feature:

feature/oauth2-login/
├── requirements.md   WHAT & WHY — user-facing behavior, constraints,
│                     acceptance criteria, non-goals. No implementation.
├── design.md         HOW — architecture, interfaces, data model, error
│                     handling, security posture, sequence diagrams.
├── tasks.md          STEPS — ordered, independently verifiable units of
│                     work, each mapped to an acceptance criterion.
└── (code + tests generated/written against the above)

Each file answers a different question and is reviewed by a different lens:

  • requirements.md is reviewed by the PM/owner and a peer: is this the right thing, and is "done" testable?
  • design.md is reviewed by an engineer/architect: will this approach hold up, is the security posture right, are boundaries clean?
  • tasks.md is the plan the implementer agent executes; each task should be small enough to verify in isolation.

Verification infrastructure comes first. Build tests, validators, and guardrails before you scale AI code generation, not after. Skipping this is the single most expensive mistake teams made in 2026 — they generated mountains of plausible code with no automated way to tell whether any of it was correct.

Signal

A good spec makes the implementer agent boring and the reviewer agent fast. If your chain produces surprising diffs, the spec was underspecified — fix the spec, not the prompt.

Do / Don't for spec-first:

DoDon't
Check specs into the repo next to the codeKeep the "real" spec in a chat history or someone's head
Version specs; review spec diffs in PRsTreat the spec as a throwaay prompt
Write acceptance criteria as testable statementsWrite aspirational prose ("should be fast and secure")
State non-goals explicitlyLeave scope open so the agent invents requirements
Define the security posture in design.mdAssume the agent will get auth/crypto right by default

Part 3 — Control Agents, Don't Vibe

"Vibe coding" — prompting an agent, eyeballing the output, accepting it because it looks plausible — is how fast wrong code enters production. The Builder discipline is control: you scope the task, manage the context, and critically review every diff against the spec.

   VIBE (uncontrolled)                CONTROL (Builder discipline)
   ──────────────────                 ────────────────────────────
   vague prompt                       scoped task tied to a tasks.md unit
   whole repo as context              curated, minimal relevant context
   accept the diff if it looks ok     diff reviewed against acceptance criteria
   "it ran, ship it"                  tests + validators must pass, then human review

Three control levers:

  1. Scope the task. One task from tasks.md, one acceptance criterion, one verifiable outcome. Large vague tasks produce large vague diffs that defeat review.
  2. Manage context. Feed the agent the relevant module, the spec, and the interface contracts — not the entire monorepo. Too much context is as harmful as too little; it dilutes attention and inflates token cost.
  3. Critically review the diff. Read AI-generated code as untrusted until proven. Trace it against the spec's acceptance criteria. Treat auth, crypto, and input-handling code as guilty until reviewed (see Module I — AI code shows materially more security and logic issues than human code).
Risk flag

Prompt injection can ride in on comments, docstrings, filenames, and config the agent reads as context. A diff that touches files the task never mentioned is a red flag, not a convenience. Review what the agent chose to change, not just the lines you expected.

Practitioner note

The reviewer's job changed. You are no longer hunting typos — the agent rarely makes those. You are checking judgment: did it satisfy the actual requirement, did it respect the boundary, did it introduce excessive agency or a silent security regression?

Part 4 — Multi-Agent Chains: The Orchestra Beats the Soloist

No single agent is trusted end-to-end. The reliable pattern is a chain of specialized roles, each with a different model and a different job, with a human owning the outcome:

   ┌───────────┐     ┌──────────────┐     ┌──────────────────┐
   │  PLANNER  │ ──▶ │  IMPLEMENTER │ ──▶ │ INDEPENDENT      │
   │  (deep    │     │  (cheap,     │     │ REVIEWER         │
   │ reasoning)│     │   fast)      │     │ (different model)│
   └───────────┘     └──────────────┘     └──────────────────┘
        │                  │                      │
   reads spec,        executes tasks.md,     checks diff vs spec,
   produces/refines   produces the diff      flags issues, does
   design + tasks                            NOT trust the author
        │                                          │
        └──────────────  HUMAN OWNS THE OUTCOME ───┘
            specifies · verifies · commits · is accountable

Why a chain and not one super-agent:

  • Independence catches errors. A reviewer model that did not write the code (ideally a different model family) is far more likely to catch a flaw than the author re-reading its own work — the same reason humans don't review their own PRs.
  • Role specialization controls cost. The planner uses an expensive reasoning model where deep thinking earns its keep; the implementer uses a cheap fast model for bulk work; the reviewer uses a capable but bounded model. Most teams waste money paying premium prices for routine implementation.
  • Each stage is verifiable. Spec → design → tasks → diff → review are checkpoints a human can inspect, rather than one opaque leap from prompt to PR.

The OAuth2 proof point. A full OAuth2 ticket, run through a planner/implementer/reviewer chain, went open-to-PR in 8 minutes at ~$1.00 total cost — versus two human-days for the same ticket. The point is not the speed. The point is that the speed only materialized because the spec was clean, the boundaries were clear, the verification existed, and the chain was orchestrated. Hand the same tools to a team with no spec discipline and you get an 8-minute path to a confidently broken PR.

Signal

When implementation stops being the constraint, the constraint moves — to spec quality, verification capacity, and reviewer attention. Staff and budget the new constraint, not the old one.

Part 5 — Agent-Ready Codebases

Note

Legacy codebases that frustrate humans frustrate agents at machine speed.

An agent navigates your repo the way a new hire would — except it does it in seconds, at scale, and without the social cue to ask "wait, which of these three auth modules is the real one?" Ambiguity that slows a human paralyzes or misleads an agent.

Four properties of an agent-ready codebase:

  1. Monorepo (or clean, discoverable structure). Cross-cutting changes that span service boundaries are far easier when the agent can see and change related code in one place.
  2. AGENTS.md / AGENT.md onboarding docs. A machine-and-human-readable file at the repo root (and optionally per-package) that tells an agent how to build, test, lint, where boundaries are, and what it must never touch. This is the agent's README. (See the template in the Artifacts section.)
  3. Clean module boundaries. Explicit interfaces and ownership so a scoped task touches one module, not a tangle. Clear boundaries are what let you give an agent minimal context.
  4. Scoped agent permissions. Least privilege for agents: which paths it may write, which commands it may run, whether it can open PRs vs. push to main, what secrets it can never see. Excessive agency is an OWASP-recognized failure mode (Module J).
   repo-root/
   ├── AGENTS.md                ← global: build/test/lint, boundaries, do-not-touch
   ├── packages/
   │   ├── auth/
   │   │   └── AGENTS.md         ← scoped: this module's conventions & owners
   │   ├── billing/
   │   └── web/
   ├── specs/                   ← versioned requirements/design/tasks
   └── .agent/permissions.yml   ← scoped paths, allowed commands, secret denylist
Practitioner note

Making a repo agent-ready also makes it human-ready. The AGENTS.md, clean boundaries, and reliable test commands you write for the agent are exactly what your next human hire wishes existed. This work is not overhead — it pays double.

Part 6 — The L1–L5 Cost Curve & Model Specialization

AI cost is not a footnote. Unmanaged token spend will rival the cloud bill within two years, and it can stall an AI program outright. Engineers at Builder level must know where their team sits and what the next level costs.

Maturity levelWhat it meansMonthly cost / engineer
L1–L2AI-assisted / augmented (autocomplete, chat)~$20
L3Spec-centric (specs drive generation)~$200
L4Agentic (chains run tasks end-to-end)~$2,000
L5Full autonomy (fleets of agents, minimal human steps)~$20,000

That is a ~1,000x range depending on how AI is deployed — not whether. Moving up the curve buys throughput; it also moves cost from headcount to compute. Workforce and budget planning must track this curve, not lag it.

Model specialization is the first-class cost lever for engineers:

   ┌────────────────────────────────────────────────────────┐
   │  PLANNING / design / hard reasoning                     │
   │     → expensive reasoning model   (small % of calls,    │
   │                                    high % of value)     │
   ├────────────────────────────────────────────────────────┤
   │  BULK IMPLEMENTATION / boilerplate / refactors          │
   │     → cheap, fast model           (most of the calls)   │
   ├────────────────────────────────────────────────────────┤
   │  REVIEW                                                 │
   │     → capable, bounded model      (different family for │
   │                                    independence)        │
   └────────────────────────────────────────────────────────┘

Most teams pay premium prices for routine work — running every call through the most expensive model. Routing by task type is where the OAuth2 ticket's ~$1.00 economics actually come from.

Risk flag

Token spend is a real engineering budget line. An ungoverned agent that loops, re-reads the whole repo, or retries on every failure can burn a month's budget in an afternoon. Caching, context discipline, and per-task model routing are cost controls, not optimizations (the production side of this lives in Module E).

Signal

Enterprise alignment is the gating factor. Engineering cannot move up the curve alone — finance must fund the token line, security must approve scoped permissions and data residency, and HR/management must adjust roles as cost shifts from headcount to compute.

Hands-On Lab / Exercises

These run on the IIIBC agent-ready sandbox repo (a small monorepo with an intentionally underspecified backlog). Pairs or trios. Each participant needs an agentic IDE/CLI and a sanctioned model account with at least two models available (one strong, one cheap).

Lab 1 — Write a Spec for a Real Ticket (50 min)

Goal: Produce a peer-reviewable requirements.md / design.md / tasks.md for a backlog ticket and pass the spec-review checklist.

  1. Pick a ticket from the sandbox backlog (suggested: "Add OAuth2 login with Google as an identity provider", mirroring the proof point).
  2. Create specs/oauth2-login/ and write the three files using the template in Artifacts. Keep requirements.md implementation-free; put architecture and security posture in design.md; break tasks.md into independently verifiable units, each tied to an acceptance criterion.
  3. Swap with another pair. Run their spec through the Spec-Review Checklist. Reject and annotate anything that fails.
  4. Revise your spec from the feedback. Commit it. The committed, reviewed spec — not the code — is the Lab 1 deliverable.

Facilitator answer key — a strong OAuth2 spec includes:

  • Requirements: success/failure user flows; account-linking behavior for an existing email; explicit non-goals (e.g., "no other IdPs this iteration"); acceptance criteria written as testable statements ("Given a valid Google token, when the user authorizes, then a session is created and last_login is updated").
  • Design: the OAuth2 authorization-code flow with PKCE; token validation and storage decisions; CSRF/state handling; what is never logged (tokens, secrets); the module boundary (auth package only); a sequence diagram.
  • Tasks: config & secrets wiring → callback route → token exchange → token validation → session creation → account-linking → tests/validators for each. Each task independently verifiable.
  • Red flags to catch in review: vague criteria ("login should work"), implementation leaking into requirements, missing error/abuse paths, no security posture, tasks too large to verify, secrets-in-logs not addressed.

Lab 2 — Run a Planner / Implementer / Reviewer Chain (60 min)

Goal: Take the committed spec to an open PR via a controlled agent chain, then review the diff like a Builder.

  1. Planner (strong model): feed it requirements.md + design.md. Have it refine/confirm tasks.md. Inspect the plan before proceeding — do not auto-advance.
  2. Implementer (cheap, fast model): execute tasks.md task-by-task with minimal scoped context (the auth package + interface contracts only). One task, one diff.
  3. Reviewer (different model family): feed it the diff + the spec. Ask it to check each acceptance criterion, flag security issues, and flag any out-of-scope file changes. The reviewer must not be the implementer.
  4. Human review (you): read the reviewer's findings and the raw diff against the acceptance criteria. Confirm tests/validators pass. Decide: open PR, send back to planner, or reject.
  5. Record wall-clock time and total token cost for the run.

Facilitator answer key / what good looks like:

  • The chain should approach the proof-point shape — minutes, not hours; cents-to-dollars, not tens of dollars — if the Lab 1 spec was clean. A messy spec produces a messy, expensive run: that is the teachable moment, not a failure.
  • Participants must articulate why the reviewer is a different model (independence) and why the implementer is cheap (most calls, routine work).
  • Catch teams that auto-accept the implementer's diff — that is vibe coding. Require an explicit human verdict against acceptance criteria.

Lab 3 — Author an AGENTS.md and Scope Permissions (40 min)

Goal: Make the sandbox repo measurably more agent-ready.

  1. Write a root AGENTS.md using the template in Artifacts: build/test/lint commands, module map, boundaries, and an explicit do-not-touch list (secrets, generated files, infra).
  2. Add a .agent/permissions.yml scoping writable paths, allowed commands, and a secret denylist.
  3. Re-run a small Lab-2 task with the new AGENTS.md in context. Compare: fewer wrong-file edits, fewer clarifying detours, lower token cost.

Facilitator answer key: the strongest submissions name owners per module, state the test command the agent must run before claiming done, and explicitly forbid touching auth/crypto without human design review.

Artifact 4 — "Control, Don't Vibe" Diff-Review Card (keep at your desk)

Before you accept an AI diff, ask:
1. Does it satisfy each acceptance criterion in the spec? (check, don't assume)
2. Did it change ONLY files the task required? (out-of-scope edits = red flag)
3. Auth / crypto / input handling — reviewed as untrusted? (Module I)
4. Any injected instructions in comments/docstrings/config it acted on? (Module J)
5. Do tests + validators pass — and do they actually test the criteria?
6. Token cost & time recorded for this task?
If any answer is "not sure" → it is not done.

Knowledge Check

  1. (MCQ) Roughly what share of engineering effort is spent actually writing code? a) 80–90% b) 60–70% c) 30–40% d) 10–20%
  2. (Short answer) A team gets a 10x speedup in coding but changes nothing else. Why is the overall productivity gain likely only ~2–3x?
  3. (MCQ) "The spec is the new code review" means: a) specs replace all testing b) you review 50 lines of versioned spec instead of rubber-stamping 500 lines of generated code c) PMs no longer write specs d) agents review their own specs
  4. (Short answer) Name the three roles in a planner/implementer/reviewer chain and state why the reviewer should be a different model from the implementer.
  5. (MCQ) Which file holds the security posture and module boundary in the three-file spec pattern? a) requirements.md b) design.md c) tasks.md d) AGENTS.md
  6. (Short answer) Give two reasons a legacy codebase that frustrates humans is even worse for agents.
  7. (MCQ) On the L1–L5 curve, approximate monthly cost per engineer at L4 (Agentic) is: a) ~$20 b) ~$200 c) ~$2,000 d) ~$20,000
  8. (Short answer) State the model-specialization rule and why it lowers cost without lowering quality.
  9. (Short answer) In the OAuth2 proof point (8 min, ~$1, vs 2 human-days), what actually made the economics work — and what would happen with the same tools but no spec discipline?
  10. (Short answer) List three things a "control, don't vibe" reviewer checks before accepting an AI-generated diff.

Answer key

  1. c — 30–40%.
  2. The 60–70% of work that is not coding (design, review, testing, incidents, requirements) is untouched; you only sped up the small slice, so the whole is bounded by the unaccelerated majority.
  3. b.
  4. Planner (deep reasoning — refines design/tasks), Implementer (cheap/fast — writes the diff), Reviewer (independent — checks diff vs spec). The reviewer must differ because an author re-reading its own work misses its own errors; independence (ideally a different model family) catches what the author cannot.
  5. b — design.md.
  6. Ambiguity that slows a human misleads an agent; the agent acts at machine speed and scale, so bad structure produces bad changes faster and in more places; no clean boundaries means you cannot give the agent minimal scoped context.
  7. c — ~$2,000.
  8. Use expensive reasoning models only for planning/hard reasoning; use cheap fast models for bulk implementation; review with a capable bounded model. Routine work doesn't need a premium model, so quality holds while cost drops — most teams overpay by running everything through the top model.
  9. The redesigned process made it work — a clean spec, clear boundaries, existing verification, and an orchestrated chain. With the same tools but no spec discipline you get an 8-minute path to a confidently broken PR (fast wrong code).
  10. Any three: satisfies each acceptance criterion; touched only required files; auth/crypto treated as untrusted; no acted-on injected instructions; tests/validators pass and actually test the criteria; cost/time recorded.

Facilitator Guide

Prep checklist

  • Stand up the IIIBC agent-ready sandbox monorepo with an underspecified backlog (include an OAuth2 ticket).
  • Confirm every participant has an agentic IDE/CLI and a sanctioned account with at least two model tiers (strong + cheap). Verify training-opt-out per Module K.
  • Pre-load the four artifacts (spec templates, AGENTS.md, spec-review checklist, diff-review card) into the sandbox.
  • Enable per-run cost/time telemetry so Lab 2 numbers are real, not estimated.
  • Have a "messy spec" example ready to demonstrate a chain producing an expensive, wrong PR.

Materials needed: sandbox repo + accounts; the four artifacts; a projector for the ASCII diagrams; a shared scoreboard for Lab 2 time/cost.

Timing guidance: Labs 1 and 2 are the spine — protect their time. If running short, trim Part 6's costing exercise to a discussion, not the labs. Lab 1's quality determines Lab 2's outcome; do not let pairs rush the spec.

Common pitfalls

  • Engineers skip straight to prompting the implementer and treat Lab 1 as paperwork. Enforce the spec-review gate: no chain run until the spec passes the checklist.
  • Teams auto-accept the implementer diff. Call it out as vibe coding in the moment; require an explicit human verdict.
  • Using the same model for implement and review. Stop it — it defeats the independence that makes the chain work.
  • Treating cost as abstract. Make Lab 2 record real dollars; the curve becomes visceral.

Discussion prompts

  • "Where is our real constraint right now — and how would we know?"
  • "What in our codebase would frustrate an agent first?"
  • "What L are we at today, and what does moving up one level cost — and who has to be aligned (finance, security, HR) for that to be real?"

Tailoring by audience

  • PMs in the room: lean into Lab 1; they own requirements.md quality and acceptance criteria.
  • Senior engineers/architects: emphasize design review and the upstream leverage shift ("become architects; review designs, not diffs").
  • Security-adjacent attendees: connect Parts 3–5 to Modules I and J (untrusted AI code, prompt injection, excessive agency, scoped permissions).
