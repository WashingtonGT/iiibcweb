Why this module exists

Most teams measured AI wrong from day one: they watched coding get faster, declared victory, and missed that coding was never the whole job. Research and field experience put coding at only 30–40 percent of engineering effort. The other 60–70 percent goes to system design, requirements clarification, code review, testing, incident response, and technical debt. A tenfold coding speedup yields only a two- to threefold overall gain when the surrounding process stays the same. One platform team at a 2025 engineering summit found that incident response alone consumed 32 percent of capacity in a single week. No coding assistant fixes that. Visibility does.

Skipping this discipline has a concrete cost. Teams get fast wrong code at scale, reviewers who rubber-stamp 500-line generated diffs, token spend that rivals the cloud bill, and "agent tech debt": code no human ever fully understood. These risk classes did not exist three years ago. Velocity without spec discipline and verification capacity is a liability.

The upside is just as proven. A chain of specialized agents planned, implemented, and reviewed a full OAuth2 ticket, taking it from open to PR in 8 minutes at roughly $1.00. The same work took two human-days (an illustrative example). The economics came from a redesigned process, not from exotic tools. The tools are a commodity; the discipline is the moat.

This module trains that discipline for growth-stage operators. It covers spec-first development, controlled agent chains, agent-ready codebases, and deliberate management of the L1–L5 cost curve.

Learning objectives

By the end of this module, participants will be able to:

  1. Locate the real constraint: measure where engineering time actually goes before claiming an AI productivity win, and explain why a tenfold coding speedup yields only about a two- to threefold overall gain.
  2. Write a peer-reviewable spec: produce a requirements.md / design.md / tasks.md set for a real ticket, checked into the repo and versioned, so that reviewers review the spec.
  3. Control an agent instead of vibe-coding: scope a task, manage context, and review an AI-generated diff against the spec instead of accepting it on sight.
  4. Run a multi-agent chain: orchestrate a planner → implementer → independent reviewer flow, and explain why no single agent is trusted end to end.
  5. Make a repo agent-ready: author an AGENTS.md, define clean module boundaries, and scope agent permissions.
  6. Place the team on the L1–L5 maturity and cost curve, and apply model specialization (expensive reasoning models for planning, cheap fast models for bulk implementation) to control token spend.
  7. Apply a spec-review checklist as a gate, and reject specs that fail it.
  8. Reproduce the OAuth2 proof point in the sandbox: take a ticket from open to PR with a chained agent run, and read the cost and time it produced.

Core content

Part 1: Coding was never the bottleneck

As coding accelerates, the constraint moves to the work before and after the code, and most organizations have not yet found where it landed. A system's output is set by its constraint, not by its strongest component. For two decades the constraint in software was writing code, and large language models (LLMs) are removing it.

   Where engineering time actually goes (directional)
   ┌──────────────────────────────────────────────────────┐
   │ Coding              ████████████  30–40%              │
   │ Surrounding work    ████████████████████████  60–70%  │
   │   incident response · system design · code review     │
   │   requirements · testing · meetings · tech debt       │
   └──────────────────────────────────────────────────────┘

   10x faster coding, process unchanged  →  ~2–3x overall gain
   (Amdahl's law applied to engineering: you can only speed up
    the part you actually accelerated.)
Signal

Instrument where time goes before you celebrate an AI productivity number. A team that learns incident response takes 32 percent of capacity has found a constraint no coding assistant can touch.

Noise

"We adopted Copilot and merged 40 percent more PRs." More PRs of what quality? Velocity reported without a paired quality metric is motion mistaken for progress.

Adopt the new measurement stack before you redesign anything. You cannot redesign what you cannot see; Module M covers these metrics in depth.

Old metricNew metric
Lines of codeAI code share (% AI-generated)
PR / raw velocityComplexity-adjusted velocity
Defect countCode turnover ratio (how much code is rewritten soon after merge)
Cost per engineerCost per ticket / cost per feature
Annual engagement surveyQuarterly DX pulse

Without these metrics, AI investment is unfalsifiable: you can neither prove nor disprove that it worked.

Practitioner note

One shift organizes this whole module: from "AI assists the engineer" to "AI executes; the engineer specifies and verifies." Specs, chains, and agent-ready repos all follow from that one sentence.

Part 2: Spec-first development: The spec is the new code review

When AI writes the code, your highest-value artifact is the specification the diff must satisfy, not the diff itself. Reviewing 50 lines of spec is worth more than reviewing 500 lines of generated code. The spec holds the intent, constraints, and acceptance criteria, and a wrong spec generates wrong code at machine speed.

Spec-first (also called spec-driven) development has one rule: check specs and tests into the repo, version them, and peer-review them exactly like code. The industry-standard shape, popularized by GitHub's Spec Kit and the wider spec-driven movement, is a three-file pattern that lives beside the feature:

feature/oauth2-login/
├── requirements.md   WHAT & WHY — user-facing behavior, constraints,
│                     acceptance criteria, non-goals. No implementation.
├── design.md         HOW — architecture, interfaces, data model, error
│                     handling, security posture, sequence diagrams.
├── tasks.md          STEPS — ordered, independently verifiable units of
│                     work, each mapped to an acceptance criterion.
└── (code + tests generated/written against the above)

Each file answers a different question, and a different reviewer checks it:

  • requirements.md: the PM or owner and a peer ask whether this is the right thing to build and whether "done" is testable.
  • design.md: an engineer or architect asks whether the approach will hold up, whether the security posture is right, and whether the boundaries are clean.
  • tasks.md: this is the plan the implementer agent executes. Keep each task small enough to verify in isolation.

Build verification infrastructure first. Put tests, validators, and guardrails in place before you scale AI code generation. In IIIBC's field experience, skipping this step was the most expensive mistake teams made in 2026: they generated mountains of plausible code with no automated way to tell whether any of it was correct.

Signal

A good spec makes the implementer agent boring and the reviewer agent fast. If your chain produces surprising diffs, the spec was underspecified. Fix the spec, not the prompt.

Do and don't for spec-first:

DoDon't
Check specs into the repo next to the codeKeep the "real" spec in a chat history or someone's head
Version specs; review spec diffs in PRsTreat the spec as a throwaway prompt
Write acceptance criteria as testable statementsWrite aspirational prose ("should be fast and secure")
State non-goals explicitlyLeave scope open so the agent invents requirements
Define the security posture in design.mdAssume the agent will get auth/crypto right by default

Part 3: Control agents, don't vibe

"Vibe coding" is how fast wrong code reaches production: you prompt an agent, eyeball the output, and accept it because it looks plausible. The Builder discipline is control. You scope the task, manage the context, and review every diff against the spec.

   VIBE (uncontrolled)                CONTROL (Builder discipline)
   ──────────────────                 ────────────────────────────
   vague prompt                       scoped task tied to a tasks.md unit
   whole repo as context              curated, minimal relevant context
   accept the diff if it looks ok     diff reviewed against acceptance criteria
   "it ran, ship it"                  tests + validators must pass, then human review

Three control levers:

  1. Scope the task. Give the agent one task from tasks.md, one acceptance criterion, and one verifiable outcome. Large, vague tasks produce large, vague diffs that defeat review.
  2. Manage context. Feed the agent the relevant module, the spec, and the interface contracts, not the entire monorepo. Too much context harms as much as too little: it dilutes attention and inflates token cost.
  3. Review the diff critically. Treat AI-generated code as untrusted until proven, and trace it against the spec's acceptance criteria. Treat auth, crypto, and input-handling code as guilty until reviewed; Module I shows that AI code carries materially more security and logic issues than human code.
Risk flag

Prompt injection can ride in on comments, docstrings, filenames, and config that the agent reads as context. A diff that touches files the task never mentioned is a red flag, not a convenience. Review what the agent chose to change, not just the lines you expected.

Practitioner note

The reviewer's job has changed. You are no longer hunting typos, because the agent rarely makes them. You are checking judgment. Did it satisfy the actual requirement? Did it respect the boundary? Did it introduce excessive agency or a silent security regression?

Part 4: Multi-agent chains: The orchestra beats the soloist

Trust no single agent end to end. The reliable pattern is a chain of specialized roles, each with its own model and job, and a human who owns the outcome:

   ┌───────────┐     ┌──────────────┐     ┌──────────────────┐
   │  PLANNER  │ ──▶ │  IMPLEMENTER │ ──▶ │ INDEPENDENT      │
   │  (deep    │     │  (cheap,     │     │ REVIEWER         │
   │ reasoning)│     │   fast)      │     │ (different model)│
   └───────────┘     └──────────────┘     └──────────────────┘
        │                  │                      │
   reads spec,        executes tasks.md,     checks diff vs spec,
   produces/refines   produces the diff      flags issues, does
   design + tasks                            NOT trust the author
        │                                          │
        └──────────────  HUMAN OWNS THE OUTCOME ───┘
            specifies · verifies · commits · is accountable

Why a chain beats one super-agent:

  • Independence catches errors. A reviewer model that did not write the code, ideally from a different model family, is far more likely to catch a flaw than an author rereading its own work. Humans don't review their own PRs for the same reason.
  • Role specialization controls cost. The planner uses an expensive reasoning model where deep thinking earns its keep. The implementer uses a cheap, fast model for bulk work, and the reviewer uses a capable but bounded model. Most teams waste money paying premium prices for routine implementation.
  • Each stage is verifiable. Spec → design → tasks → diff → review gives a human checkpoints to inspect, instead of one opaque leap from prompt to PR.

The OAuth2 proof point shows that the process, not the speed, carries the value. A planner, implementer, and reviewer chain took a full OAuth2 ticket from open to PR in 8 minutes at about $1.00 total cost, against two human-days for the same ticket. That speed appeared only because the spec was clean, the boundaries were clear, verification existed, and someone orchestrated the chain. Hand the same tools to a team with no spec discipline and you get an 8-minute path to a confidently broken PR.

Signal

When implementation stops being the constraint, the constraint moves to spec quality, verification capacity, and reviewer attention. Staff and budget the new constraint, not the old one.

Part 5: Agent-ready codebases

Note

Legacy codebases that frustrate humans frustrate agents at machine speed.

Ambiguity that slows a human will stall or mislead an agent. An agent explores your repo the way a new hire would, except in seconds, at scale, and without the social cue to ask, "Wait, which of these three auth modules is the real one?"

Four properties of an agent-ready codebase:

  1. Monorepo (or a clean, discoverable structure). Changes that cross service boundaries are far easier when the agent can see and change related code in one place.
  2. AGENTS.md / AGENT.md onboarding docs. Put a file that both machines and humans can read at the repo root, and optionally in each package. It tells an agent how to build, test, and lint, where the boundaries are, and what it must never touch. This is the agent's README; see the template in the artifacts section.
  3. Clean module boundaries. Explicit interfaces and ownership mean a scoped task touches one module, not a tangle. Clear boundaries are what let you give an agent minimal context.
  4. Scoped agent permissions. Give agents least privilege: which paths they may write, which commands they may run, whether they can open PRs or push to main, and which secrets they can never see. Excessive agency is a failure mode that OWASP recognizes (Module J).
   repo-root/
   ├── AGENTS.md                ← global: build/test/lint, boundaries, do-not-touch
   ├── packages/
   │   ├── auth/
   │   │   └── AGENTS.md         ← scoped: this module's conventions & owners
   │   ├── billing/
   │   └── web/
   ├── specs/                   ← versioned requirements/design/tasks
   └── .agent/permissions.yml   ← scoped paths, allowed commands, secret denylist
Practitioner note

Making a repo agent-ready also makes it human-ready. The AGENTS.md, clean boundaries, and reliable test commands you write for the agent are exactly what your next human hire wishes existed. This work pays twice; it is not overhead.

Part 6: The L1–L5 cost curve and model specialization

Treat AI cost as a first-order engineering concern. Unmanaged token spend will rival the cloud bill within two years, and it can stall an AI program outright. Builder-level engineers must know where their team sits on the curve and what the next level costs.

Maturity levelWhat it meansMonthly cost / engineer
L1–L2AI-assisted / augmented (autocomplete, chat)~$20
L3Spec-centric (specs drive generation)~$200
L4Agentic (chains run tasks end-to-end)~$2,000
L5Full autonomy (fleets of agents, minimal human steps)~$20,000

How you deploy AI, not whether you do, sets cost across a roughly 1,000-fold range. Moving up the curve buys throughput, and it also shifts cost from headcount to compute. Workforce and budget planning must track this curve, not lag behind it.

Model specialization is the engineer's main cost lever:

   ┌────────────────────────────────────────────────────────┐
   │  PLANNING / design / hard reasoning                     │
   │     → expensive reasoning model   (small % of calls,    │
   │                                    high % of value)     │
   ├────────────────────────────────────────────────────────┤
   │  BULK IMPLEMENTATION / boilerplate / refactors          │
   │     → cheap, fast model           (most of the calls)   │
   ├────────────────────────────────────────────────────────┤
   │  REVIEW                                                 │
   │     → capable, bounded model      (different family for │
   │                                    independence)        │
   └────────────────────────────────────────────────────────┘

Most teams pay premium prices for routine work by running every call through the most expensive model. Routing by task type is where the OAuth2 ticket's $1.00 economics actually come from.

Risk flag

Token spend is a real engineering budget line. An ungoverned agent that loops, rereads the whole repo, or retries on every failure can burn a month's budget in an afternoon. Caching, context discipline, and per-task model routing are cost controls, not optimizations; Module E covers the production side.

Signal

Enterprise alignment decides how far engineering can climb, and engineering cannot climb the curve alone. Finance must fund the token line, security must approve scoped permissions and data residency, and HR and management must adjust roles as cost shifts from headcount to compute.

Hands-on lab and exercises

Run these labs on the IIIBC agent-ready sandbox repo, a small monorepo with a deliberately underspecified backlog. Work in pairs or trios. Each participant needs an agentic IDE or CLI and a sanctioned model account with at least two models available (one strong, one cheap).

Lab 1: Write a spec for a real ticket (50 min)

Goal: Produce a peer-reviewable requirements.md / design.md / tasks.md for a backlog ticket, and pass the spec-review checklist.

  1. Pick a ticket from the sandbox backlog. We suggest "Add OAuth2 login with Google as an identity provider", which mirrors the proof point.
  2. Create specs/oauth2-login/ and write the three files from the template in the artifacts section. Keep requirements.md free of implementation detail, and put architecture and security posture in design.md. Break tasks.md into independently verifiable units, each tied to an acceptance criterion.
  3. Swap with another pair. Run their spec through the spec-review checklist, and reject and annotate anything that fails.
  4. Revise your spec from the feedback and commit it. The committed, reviewed spec, not the code, is the Lab 1 deliverable.

Facilitator answer key: a strong OAuth2 spec includes:

  • Requirements: success and failure user flows; account-linking behavior for an existing email; explicit non-goals (e.g., "no other IdPs this iteration"); acceptance criteria written as testable statements ("Given a valid Google token, when the user authorizes, then a session is created and last_login is updated").
  • Design: the OAuth2 authorization-code flow with PKCE; token validation and storage decisions; CSRF and state handling; what is never logged (tokens, secrets); the module boundary (auth package only); a sequence diagram.
  • Tasks: config and secrets wiring → callback route → token exchange → token validation → session creation → account-linking → tests and validators for each. Each task is independently verifiable.
  • Red flags to catch in review: vague criteria ("login should work"), implementation leaking into requirements, missing error and abuse paths, no security posture, tasks too large to verify, and secrets-in-logs left unaddressed.

Lab 2: Run a planner, implementer, and reviewer chain (60 min)

Goal: Take the committed spec to an open PR through a controlled agent chain, then review the diff like a Builder.

  1. Planner (strong model): feed it requirements.md + design.md, and have it refine or confirm tasks.md. Inspect the plan before you proceed; do not auto-advance.
  2. Implementer (cheap, fast model): execute tasks.md one task at a time with minimal scoped context (the auth package and interface contracts only). One task, one diff.
  3. Reviewer (different model family): feed it the diff and the spec. Ask it to check each acceptance criterion and to flag security issues and any out-of-scope file changes. The reviewer must not be the implementer.
  4. Human review (you): read the reviewer's findings and the raw diff against the acceptance criteria. Confirm that tests and validators pass. Then decide: open the PR, send it back to the planner, or reject it.
  5. Record wall-clock time and total token cost for the run.

Facilitator answer key: what good looks like:

  • If the Lab 1 spec was clean, the chain should approach the proof-point shape: minutes, not hours; cents to dollars, not tens of dollars. A messy spec produces a messy, expensive run. Treat that as the teachable moment, not a failure.
  • Participants must explain why the reviewer is a different model (independence) and why the implementer is cheap (it makes most of the calls, on routine work).
  • Catch teams that auto-accept the implementer's diff; that is vibe coding. Require an explicit human verdict against the acceptance criteria.

Lab 3: Author an AGENTS.md and scope permissions (40 min)

Goal: Make the sandbox repo measurably more agent-ready.

  1. Write a root AGENTS.md from the template in the artifacts section: build, test, and lint commands, a module map, boundaries, and an explicit do-not-touch list (secrets, generated files, infra).
  2. Add a .agent/permissions.yml that scopes writable paths, allowed commands, and a secret denylist.
  3. Rerun a small Lab 2 task with the new AGENTS.md in context. Compare the results: you should see fewer wrong-file edits, fewer clarifying detours, and lower token cost.

Facilitator answer key: the strongest submissions name an owner for each module, state the test command the agent must run before it claims done, and explicitly forbid touching auth or crypto without human design review.

Artifact 4: "Control, don't vibe" diff-review card (keep it at your desk)

Before you accept an AI diff, ask:
1. Does it satisfy each acceptance criterion in the spec? (check, don't assume)
2. Did it change ONLY files the task required? (out-of-scope edits = red flag)
3. Auth / crypto / input handling — reviewed as untrusted? (Module I)
4. Any injected instructions in comments/docstrings/config it acted on? (Module J)
5. Do tests + validators pass — and do they actually test the criteria?
6. Token cost & time recorded for this task?
If any answer is "not sure" → it is not done.

Knowledge check

  1. (MCQ) Roughly what share of engineering effort goes to actually writing code? a) 80–90 percent b) 60–70 percent c) 30–40 percent d) 10–20 percent
  2. (Short answer) A team gets a tenfold coding speedup but changes nothing else. Why is the overall productivity gain likely to be only about two to three times?
  3. (MCQ) "The spec is the new code review" means: a) specs replace all testing b) you review 50 lines of versioned spec instead of rubber-stamping 500 lines of generated code c) PMs no longer write specs d) agents review their own specs
  4. (Short answer) Name the three roles in a planner, implementer, and reviewer chain, and state why the reviewer should be a different model from the implementer.
  5. (MCQ) In the three-file spec pattern, which file holds the security posture and module boundary? a) requirements.md b) design.md c) tasks.md d) AGENTS.md
  6. (Short answer) Give two reasons why a legacy codebase that frustrates humans is even worse for agents.
  7. (MCQ) On the L1–L5 curve, the approximate monthly cost per engineer at L4 (Agentic) is: a) ~$20 b) ~$200 c) ~$2,000 d) ~$20,000
  8. (Short answer) State the model-specialization rule, and explain why it lowers cost without lowering quality.
  9. (Short answer) In the OAuth2 proof point (8 min, ~$1, vs 2 human-days), what actually made the economics work, and what would happen with the same tools but no spec discipline?
  10. (Short answer) List three things a "control, don't vibe" reviewer checks before accepting an AI-generated diff.

Answer key

  1. c: 30–40 percent.
  2. The 60–70 percent of work that is not coding (design, review, testing, incidents, requirements) stays untouched. You sped up only the small slice, so the unaccelerated majority bounds the whole.
  3. b.
  4. Planner (deep reasoning; refines design and tasks), Implementer (cheap and fast; writes the diff), and Reviewer (independent; checks the diff against the spec). The reviewer must differ because an author rereading its own work misses its own errors. Independence, ideally from a different model family, catches what the author cannot.
  5. b: design.md.
  6. Ambiguity that slows a human misleads an agent. The agent acts at machine speed and scale, so bad structure produces bad changes faster and in more places. Without clean boundaries, you cannot give the agent minimal scoped context.
  7. c: ~$2,000.
  8. Use expensive reasoning models only for planning and hard reasoning, cheap fast models for bulk implementation, and a capable bounded model for review. Routine work doesn't need a premium model, so quality holds while cost drops. Most teams overpay by running everything through the top model.
  9. The redesigned process made it work: a clean spec, clear boundaries, existing verification, and an orchestrated chain. The same tools without spec discipline give you an 8-minute path to a confidently broken PR (fast wrong code).
  10. Any three: it satisfies each acceptance criterion; it touched only required files; auth and crypto code was treated as untrusted; it acted on no injected instructions; tests and validators pass and actually test the criteria; cost and time are recorded.

Timing guidance: Labs 1 and 2 are the spine of the day, so protect their time. If you run short, cut Part 6's costing exercise to a discussion and leave the labs intact. Lab 1's quality determines Lab 2's outcome; don't let pairs rush the spec.

Common pitfalls

  • Engineers skip straight to prompting the implementer and treat Lab 1 as paperwork. Enforce the spec-review gate: no chain run until the spec passes the checklist.
  • Teams auto-accept the implementer's diff. Call it vibe coding in the moment, and require an explicit human verdict.
  • Teams use the same model to implement and review. Stop it: it defeats the independence that makes the chain work.
  • Teams treat cost as abstract. Make Lab 2 record real dollars, and the curve becomes tangible.

Discussion prompts

  • "Where is our real constraint right now, and how would we know?"
  • "What in our codebase would frustrate an agent first?"
  • "Which L are we at today, what does moving up one level cost, and who has to be aligned (finance, security, HR) for that to be real?"

Tailoring by audience

  • PMs in the room: lean into Lab 1, because they own requirements.md quality and acceptance criteria.
  • Senior engineers and architects: emphasize design review and the shift of influence upstream ("become architects; review designs, not diffs").
  • Security-adjacent attendees: connect Parts 3–5 to Modules I and J (untrusted AI code, prompt injection, excessive agency, scoped permissions).
